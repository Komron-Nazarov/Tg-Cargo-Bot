# Cargo Bot

Telegram-бот на Python для регистрации клиентов и обработки заявок на доставку. Один код поддерживает два режима развёртывания: Railway через long polling и Render Web Service через webhook.

## Возможности текущего этапа

- регистрация клиента по Telegram user ID;
- постоянный уникальный Client ID в формате `C000001`;
- профиль клиента;
- персонализированное сообщение с адресом китайского склада;
- предварительная регистрация Chinese Tracking Number;
- список и безопасная отмена ошибочных трек-номеров;
- админский поиск по трек-номеру и Client ID;
- складская приёмка администратором по команде `/receive`;
- постоянный уникальный Cargo ID в формате `CG000001`;
- сохранение фактического веса, объёма, количества мест и описания;
- от 1 до 10 фотографий груза через Telegram file ID;
- уведомление клиента о приёмке и раздел «🚚 Мои грузы»;
- админский список и поиск принятых Cargo;
- консолидация 2–50 Cargo одного клиента на китайском складе;
- постоянный Consolidation ID вида `CS000001`;
- итоговые параметры и фотографии объединённой упаковки;
- клиентский раздел «🔗 Мои консолидации»;
- создание партии отправки из отдельных Cargo и готовых Consolidation;
- постоянный Shipment ID вида `SH000001`;
- фиксация фактического выезда из Китая и уведомление каждого клиента только о его грузах;
- клиентский раздел «🚛 Мои отправления»;
- последовательное движение Shipment: выезд, транзит, прибытие и таможня;
- история статусов Shipment без раскрытия внутренних примечаний клиенту;
- создание и просмотр существующих заявок;
- управление статусами заявок администратором.

После регистрации Client ID необходимо указывать на посылке или в данных получателя. Повторный `/start` не создаёт нового клиента.

## Chinese Tracking Number

Зарегистрированный клиент открывает «🔎 Китайские трек-номера», добавляет номер продавца и подтверждает его. Бот нормализует латинские буквы в верхний регистр, удаляет пробелы и защищает номера от дубликатов.

Новый номер получает статус «Ожидается на складе». Ошибочно добавленную запись можно отменить без физического удаления. После складской приёмки номер получает статус «Принят на китайском складе» и больше не может быть отменён или принят повторно.

Даже после регистрации трек-номера продавец должен указать Client ID клиента на посылке или в данных получателя.

Администратору доступны:

```text
/trackings
/tracking <трек-номер или Client ID>
/receive <трек-номер>
/cargos
/cargo <Cargo ID>
/consolidate <Cargo ID> <Cargo ID> [...]
/consolidations
/consolidation <Consolidation ID>
/dispatch <Cargo ID или Consolidation ID> [...]
/shipments
/shipment <Shipment ID>
/advance <Shipment ID>
```

## Client ID, Tracking Number, Cargo ID, Consolidation ID и Shipment ID

- `Client ID` (`C000001`) определяет клиента и выдаётся один раз при регистрации.
- `Chinese Tracking Number` выдаёт продавец или китайская служба доставки; клиент заранее добавляет его в бот.
- `Cargo ID` (`CG000001`) создаёт бот только после фактического приёма посылки на китайском складе.
- `Consolidation ID` (`CS000001`) создаётся после физического объединения нескольких Cargo одного клиента.
- `Shipment ID` (`SH000001`) создаётся при фактическом выезде партии из Китая и может объединять грузы разных клиентов.

Эти идентификаторы не заменяют друг друга. Публичные ID не зависят от Telegram username и создаются PostgreSQL identity.

## Складская приёмка

Сотрудником склада на текущем этапе считается Telegram-пользователь из `ADMIN_ID`. Он запускает `/receive <трек-номер>`, подтверждает найденного клиента, вводит описание, фактический вес, объём и количество мест, затем добавляет 1–10 фотографий и подтверждает создание Cargo.

Cargo, фотографии и смена статуса tracking сохраняются одной транзакцией PostgreSQL. При ошибке ни одна часть приёмки не остаётся в базе. Повторное подтверждение не создаёт второй Cargo.

Фотографии не скачиваются на сервер и не хранятся в PostgreSQL как бинарные данные. База хранит только Telegram `file_id` и `file_unique_id`, через которые бот повторно отправляет фотографии клиенту и администратору.

После успешной приёмки клиент получает уведомление и может открыть груз через кнопку «🚚 Мои грузы».

## Консолидация

Администратор запускает `/consolidate CG000001 CG000002`, после чего бот проверяет, что Cargo существуют, принадлежат одному клиенту, приняты в Китае и ещё не консолидированы. Сотрудник вводит итоговые параметры после переупаковки и добавляет 1–10 фотографий.

Consolidation, её Cargo, фотографии и новые статусы Cargo сохраняются одной PostgreSQL-транзакцией. Блокировки Cargo берутся в стабильном порядке, а уникальность `consolidation_items.cargo_id` не позволяет включить один Cargo в две консолидации.

После создания клиент получает уведомление и видит запись через «🔗 Мои консолидации». Исходные Cargo остаются в истории со статусом «Консолидирован».

## Отправление из Китая

Администратор запускает `/dispatch CG000003 CS000001`. Shipment может содержать отдельные Cargo, которые не входят в консолидацию, и готовые Consolidation, в том числе разных клиентов. Бот проверяет статусы и отсутствие предыдущей отправки, показывает суммарные параметры, затем запрашивает транспорт, reference и примечание.

Shipment, его items и статусы всех затронутых Cargo и Consolidation сохраняются одной транзакцией. Публичный Shipment ID создаётся PostgreSQL identity. После подтверждения каждый клиент получает одно отдельное уведомление только со своими Cargo, Consolidation и tracking-номерами. Раздел «🚛 Мои отправления» также не раскрывает данные других клиентов общей партии.

После выезда администратор последовательно выполняет `/advance SH000001`. Допустимы только переходы «Выехал из Китая» → «В пути» → «Прибыл в Таджикистан» → «На таможенном оформлении» → «Таможня пройдена». Пропуск этапов и движение назад запрещены.

Каждый переход одной транзакцией создаёт событие истории и обновляет Shipment, отдельные Cargo, Consolidation и Cargo внутри неё. После успешного изменения каждый клиент получает одно уведомление только со своими грузами. Внутреннее примечание события доступно администратору, но не показывается клиенту.

Распределение по Душанбе и Худжанду, пункты выдачи, получение и оплата пока не реализованы.

## Общие переменные окружения

```dotenv
BOT_TOKEN=
ADMIN_ID=
DB_HOST=
DB_PORT=5432
DB_NAME=
DB_USER=
DB_PASSWORD=
DB_SSL=require
DEPLOY_MODE=polling
CHINA_WAREHOUSE_ADDRESS=
CHINA_WAREHOUSE_RECIPIENT=
CHINA_WAREHOUSE_PHONE=
```

Секреты нельзя добавлять в Git. Для Supabase используется `DB_SSL=require`; для локального PostgreSQL без SSL — `DB_SSL=disable`. Переменные китайского склада необязательны: если `CHINA_WAREHOUSE_ADDRESS` пуст, бот продолжит работать и покажет клиенту, что адрес ещё не настроен.

## Railway: long polling

Для Railway достаточно добавить к общим переменным:

```dotenv
DEPLOY_MODE=polling
```

Команда запуска остаётся общей:

```text
python main.py
```

Перед запуском polling приложение удаляет ранее установленный webhook без удаления накопившихся обновлений.

## Render: webhook

Создайте Render Web Service из того же репозитория и используйте Dockerfile. Добавьте общие переменные и:

```dotenv
DEPLOY_MODE=webhook
WEBHOOK_BASE_URL=https://your-service.onrender.com
WEBHOOK_PATH=/telegram/webhook
WEBHOOK_SECRET=replace-with-random-secret
PORT=10000
```

`WEBHOOK_BASE_URL` должен быть внешним HTTPS-адресом Render. `WEBHOOK_SECRET` — отдельная случайная строка из букв, цифр, `_` и `-`; это не `BOT_TOKEN`.

Render передаёт `PORT` автоматически. Приложение слушает `0.0.0.0:$PORT`, устанавливает webhook при старте и намеренно не удаляет его при shutdown, чтобы следующий Telegram webhook мог разбудить уснувший сервис.

Проверка HTTP-сервиса:

```text
GET https://your-service.onrender.com/health
```

Ожидаемый ответ:

```json
{"status": "ok"}
```

`/health` не обращается к PostgreSQL.

Render Free засыпает после периода без входящих запросов. Первое сообщение после сна может обрабатываться с задержкой из-за холодного запуска; Telegram обычно повторяет недоставленный webhook.

## Важное ограничение Telegram

**Не запускайте Railway polling и Render webhook одновременно с одним `BOT_TOKEN`.** Telegram не поддерживает одновременную нормальную работу webhook и `getUpdates` для одного бота.

Для параллельного сравнения используйте два тестовых бота с разными токенами. Предпочтительно использовать и отдельный тестовый проект Supabase.

Если токен один:

- Railway → Render: остановите Railway, задайте Render-переменные и запустите Render;
- Render → Railway: остановите Render, установите `DEPLOY_MODE=polling` и запустите Railway — приложение само удалит webhook.

## Проверка установленного webhook

Telegram Bot API позволяет проверить состояние webhook методом `getWebhookInfo`. Подставляйте токен только локально и не сохраняйте команду с реальным токеном в Git или публичных логах:

```text
https://api.telegram.org/bot<YOUR_BOT_TOKEN>/getWebhookInfo
```

В polling-режиме поле `url` должно быть пустым. В Render webhook-режиме оно должно содержать адрес из `WEBHOOK_BASE_URL` и `WEBHOOK_PATH`.

## Миграции

Миграции из `migrations/sql` выполняются по имени файла. Версии и контрольные суммы записываются в `schema_migrations`.

Правила:

1. Не редактировать уже применённую миграцию.
2. Для изменения схемы создавать следующий SQL-файл.
3. Перед production-миграцией сделать резервную копию.
4. Сначала проверять миграции на копии базы.

Первая миграция создаёт исходную таблицу `orders`. Миграция `002_create_clients.sql` отдельно создаёт клиентов и не изменяет `orders`. Client ID формируется из PostgreSQL identity, поэтому параллельные регистрации не используют небезопасный `MAX + 1`.

Миграция `003_create_china_trackings.sql` создаёт отдельную таблицу предварительно заявленных китайских трек-номеров. Уникальное ограничение PostgreSQL защищает от одновременного добавления одного номера разными пользователями. Миграция не изменяет `orders` или `clients`.

Миграция `004_create_cargos.sql` расширяет статусы tracking значением `received`, создаёт таблицы `cargos` и `cargo_photos`, а также их индексы и ограничения. Cargo ID формируется из PostgreSQL identity. Один tracking может принадлежать только одному Cargo. Миграция не изменяет таблицы `orders` и `clients` и не редактирует миграции `001–003`.

Миграция `005_create_consolidations.sql` добавляет Cargo-статус `consolidated` и создаёт `consolidations`, `consolidation_items` и `consolidation_photos`. Consolidation ID формируется из PostgreSQL identity. Миграция не редактирует миграции `001–004` и не изменяет `orders`, `clients` или `china_trackings`.

Миграция `006_create_shipments.sql` добавляет статус выезда для Cargo и Consolidation, создаёт `shipments` и `shipment_items`, а также ограничения, не позволяющие повторно отправить один объект. Shipment ID формируется из PostgreSQL identity. Миграция не редактирует `001–005` и не изменяет `orders`, `clients` или `china_trackings`.

Миграция `007_create_shipment_events.sql` расширяет статусы Shipment, Cargo и Consolidation и создаёт неизменяемую историю `shipment_events`. Уникальность `(shipment_id, to_status)` защищает от повторного создания этапа. Миграция не редактирует `001–006` и не изменяет `orders`, `clients`, `china_trackings`, фотографии или состав Shipment.

## Ручная проверка

1. Новый пользователь отправляет `/start`, проходит регистрацию и получает Client ID.
2. Повторный `/start` показывает тот же Client ID без повторной регистрации.
3. Кнопка «👤 Мой профиль» показывает Client ID, имя, телефон и город.
4. Кнопка «🏭 Адрес склада в Китае» показывает настроенный адрес и Client ID либо понятное сообщение, если адрес не задан.
5. «📦 Новая заявка» и «📋 Мои заявки» продолжают прежний сценарий.
6. Администратор проверяет `/orders` и смену статуса заявки.
7. Клиент открывает «🔎 Китайские трек-номера», добавляет `LP123456789CN` и подтверждает.
8. Повторное добавление того же номера показывает сообщение о дубликате.
9. «📋 Мои трек-номера» показывает номер, дату и статус.
10. Клиент отменяет номер и проверяет, что он остался в истории со статусом «Отменён».
11. Администратор проверяет `/trackings`, `/tracking LP123456789CN` и `/tracking C000001`.
12. Создать новый tracking со статусом «Ожидается на складе» и выполнить `/receive LP123456789CN` от аккаунта `ADMIN_ID`.
13. Подтвердить начало, ввести описание, вес `2,5`, объём `0,035`, количество мест `1` и отправить 1–10 фотографий.
14. Проверить итоговую карточку и нажать «Принять и создать Cargo ID».
15. Убедиться, что создан ID вида `CG000001`, клиент получил текст и фотографии, а tracking стал принятым.
16. Клиент открывает «🚚 Мои грузы» и фотографии Cargo.
17. Администратор проверяет `/cargos` и `/cargo CG000001`.
18. Повторный `/receive LP123456789CN` сообщает, что номер уже принят.
19. Отменённый tracking не принимается командой `/receive`.
20. Проверить, что профиль, старые заявки, `/orders`, webhook Render и polling Railway работают как прежде.
21. Создать минимум два Cargo одного клиента со статусом «Принят на китайском складе».
22. Администратор выполняет `/consolidate CG000001 CG000002` и проверяет предварительную карточку.
23. Ввести описание, итоговый вес, объём или `/skip`, количество мест и добавить фотографии.
24. Подтвердить создание и получить Consolidation ID вида `CS000001`.
25. Проверить уведомление клиента и кнопку «🔗 Мои консолидации».
26. Администратор проверяет `/consolidations` и `/consolidation CS000001`.
27. Убедиться, что исходные Cargo показываются как «Консолидирован».
28. Повторная консолидация тех же Cargo не создаёт новую запись.
29. Проверить запрет объединения Cargo разных клиентов.
30. Подготовить отдельный Cargo и готовую Consolidation, затем выполнить `/dispatch CG000003 CS000001`.
31. Проверить предварительную карточку, выбрать транспорт, ввести reference или `/skip`, примечание или `/skip`.
32. Подтвердить выезд и получить Shipment ID вида `SH000001`.
33. Проверить, что каждый клиент получил одно уведомление только со своими грузами.
34. Клиент открывает «🚛 Мои отправления» и не видит данные других клиентов партии.
35. Администратор проверяет `/shipments` и `/shipment SH000001`.
36. Повторная отправка тех же Cargo или Consolidation не создаёт новый Shipment.
37. Проверить прежние Cargo, Consolidation, tracking, профиль, заявки и `/orders`.
38. Выполнить `/advance SH000001`, добавить примечание или `/skip` и подтвердить статус «В пути».
39. Проверить отдельные уведомления клиентов и историю в «🚛 Мои отправления».
40. Последовательно повторить `/advance SH000001` для прибытия, начала таможни и завершения таможни.
41. Проверить, что после «Таможня пройдена» следующий переход запрещён.
42. Проверить историю и внутренние примечания через `/shipment SH000001`.
43. Убедиться, что `/shipments` показывает актуальные статусы.
